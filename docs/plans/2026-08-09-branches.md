# Plan : Gérer plusieurs points de vente (E1)

## Contexte facture.gn
- Module : Trust Context (`apps/trust-api`) — nouvelle entité `Branch`, extension d'une méthode déjà testée (`createDraft()`, déjà étendue une fois pour `customerId`/C6)
- Persona affecté : organisation multi-sites (boutique + entrepôt, ou plusieurs agences) qui veut suivre son chiffre d'affaires par point de vente
- Données sensibles manipulées : aucune (nom + type de succursale, rien de personnel)
- Impact réglementaire : ADR-037 — la numérotation légale (`Invoice.number`, séquence OHADA Article 23) reste STRICTEMENT au niveau organisation, jamais par branche — invariant déjà respecté nativement (`InvoiceSequence` est déjà clé par `organizationId`+`year`, jamais par branche, aucun changement requis ici)

## Investigation préalable
Backlog (texte exact) : *"E1 — Gérer plusieurs points de vente `[SHOULD]`. En tant qu'organisation multi-sites, je veux rattacher mes factures à des succursales, afin de suivre le CA par point de vente. - branch sous organization. Réf : ADR-037."*

ADR-037 (texte exact) : *"Multi-succursale, numérotation au niveau organisation. Décision : branch sous organization, number jamais par branche."*

**Découverte structurante** : `Invoice.branchId` (schema.prisma) existe déjà comme `String?` brut — mais AUCUN modèle `Branch` n'existe dans tout le schema (grep confirmé), et AUCUN chemin applicatif ne l'écrit jamais (grep confirmé, aucune référence dans `apps/`). Exactement le même pattern que `Customer`/`customerId` avant C6 (mergé cette session) — cette story applique la MÊME méthode déjà éprouvée.

ERD-facture-gn.md §2.1 (`BRANCH`, lignes 90-97) donne la définition complète : `id, organization_id, name, type (enum: boutique/entrepot/agence/en_ligne)`. Modèle volontairement minimal, aucun champ supplémentaire documenté.

**Décision de scope sur "suivre le CA par point de vente"** : contrairement à C6 (`runningBalance` = solde encore DÛ, agrégat sur `amountDue`), le "CA" (chiffre d'affaires) d'une succursale est le TOTAL facturé, pas le solde impayé — agrégat sur `Invoice.totalTtc` pour les factures `issued`/`partially_paid`/`paid` (documentType `invoice` uniquement — jamais un proforma/devis, qui ne constituent jamais un CA réel). `voided` et `draft` exclus (jamais facturés réellement).

**Décision de scope sur la numérotation** : ADR-037 est explicite — "number jamais par branche". Vérifié : `InvoiceSequence` (schema.prisma) est déjà unique par `[organizationId, year]`, jamais par branche — AUCUN changement requis sur `InvoiceNumberingService`, invariant déjà respecté nativement par la structure existante.

## Problème (en 3 lignes max)
Une organisation avec plusieurs points de vente ne peut pas savoir quelle part de son chiffre d'affaires provient de quel site — `Invoice.branchId` existe mais ne pointe vers rien, et aucun agrégat par succursale n'existe.

## Solution retenue (en 5 lignes max)
Nouveau modèle `Branch` (id, organizationId, name, type). `POST /branches` (création, même trio de rôles que `POST /customers`). `create-invoice.dto.ts` accepte un `branchId` optionnel (validé : même organisation, même discipline que `customerId`/C6). `GET /branches/:id` retourne la succursale + `totalRevenue` calculé à la volée (`SUM(totalTtc)` sur les factures `issued`/`partially_paid`/`paid` de type `invoice`).

## Alternatives écartées
Stocker `totalRevenue` comme colonne persistée — écartée pour la même raison que `runningBalance` (C6) : source de vérité dupliquée, aucun précédent de ce genre accepté dans ce repo. Restreindre la numérotation par branche — explicitement écarté par ADR-037 lui-même, aucune ambiguïté.
